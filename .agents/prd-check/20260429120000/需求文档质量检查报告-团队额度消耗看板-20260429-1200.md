## 评审上下文

> 检查前对该需求的全局理解，后续所有检查基于此上下文判断深度。

| 维度 | 理解 |
|------|------|
| 业务意图 | 让组织管理员在现有 Usage Analytics 看板中直接看到团队 Credit 余额，无需跳转到 Payment Details 页面，快速判断是否需要充值。痛点：管理员当前需离开看板去 Payment Details 查看余额，体验割裂。 |
| 目标用户 | 组织管理员（owner / billing_manager 角色），仅 1 类角色。 |
| 核心流程 | 管理员进入 `/organizations/[id]/usage-details` → SummarySection 中新增 Credit 余额卡片（第 6 个卡片）→ 看到当前余额（时点值）。仅 `canViewAllOrgUsers` 为 true 时可见。 |
| 成功指标 | 「管理员在 Usage Analytics 看板中能直接看到 Credit 余额，无需跳转到 Payment Details 页面查看」（文档自述为推断，用户未提供量化指标）。 |
| 技术约束 | Credit 余额数据在 Postgres（`organizations.total_microdollars_acquired - microdollars_used`），现有 Usage Analytics 数据管道（`getSummary`/`getTimeseries`/`getBreakdown`）全部基于 Snowflake。需独立 Postgres 查询路径，不能混入 Snowflake 查询。 |
| 最大风险 | 双数据源语义一致性：Cost 卡片（Snowflake 时间段聚合）与 Credit 余额卡片（Postgres 时点值）口径不同，用户可能困惑为何数值不可直接比较。文档已识别此风险并提出 tooltip 缓解方案。 |

## 深度洞察

> 三维度检查回答了"文档写得怎么样"，以下洞察回答"文档缺了什么"。

### 缺失的隐含需求

1. **余额为零或负数的展示**
   - 证据：文档「范围内」描述了新增 Credit 余额卡片，但未提及边缘情况。
   - 缺失：未提及余额为 0 或负数（超额使用）时的 UI 展示。Credit 余额为 0 是需要充值的强烈信号，应该有差异化展示（如红色高亮、充值引导）。
   - 后果：开发时按默认数值展示，用户可能忽略余额告警，错过充值时机。
   - 建议：补充余额阈值告警展示规则（如余额 < 某阈值时黄色警告，余额 ≤ 0 时红色+充值入口）。

2. **数据加载失败时的降级策略**
   - 证据：文档「仓库影响地图」描述了新 tRPC 过程独立查询 Postgres。
   - 缺失：未提及 Postgres 查询失败时卡片的行为——是隐藏卡片、显示错误占位符、还是阻塞整个 SummarySection 渲染？
   - 后果：Postgres 故障可能导致整个 Usage Analytics 页面崩溃，影响其他正常功能（Snowflake 数据）。
   - 建议：明确降级策略：Credit 余额卡片独立加载，失败时隐藏卡片或显示「余额暂不可用」提示，不影响其他卡片渲染。

### 跨章节矛盾

无。（文档内部逻辑一致，范围内/范围外/仓库影响地图之间无矛盾。）

### 实现可行性疑点

1. **双数据源一致性风险已识别但缓解方案不完整**
   - 疑点：文档「风险与预研工作」已识别双数据源一致性风险，并建议在 tooltip 中说明口径差异。但仅靠 tooltip 可能不够——用户可能不会 hover 查看 tooltip，直接在视觉上对比两个数值产生困惑。
   - 建议：考虑在卡片上直接标注「实时余额」标签，与 Cost 卡片的「所选时间段」形成视觉区分，降低误读概率。

2. **余额实时性 vs 查询性能**
   - 疑点：文档将 Credit 余额定义为「当前余额（时点值）」，暗示每次页面加载都查询 Postgres。但未讨论高并发场景下（多个管理员同时查看）对 Postgres 的查询压力。
   - 建议：评估是否需要加缓存层（如短 TTL 的 Redis 缓存），或确认当前 organizations 表查询性能足以支撑预期并发。
